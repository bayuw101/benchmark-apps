01 · Run lifecycle

One run, from the engineer's form to the final report. A run is checked three times before load starts: by the API at creation, again at Start (with a preflight check), and by each runner pod just before k6 launches. The Next.js route handlers record and check the run; a separate worker process creates the k6 Operator TestRun in Kubernetes, and the operator starts one runner pod per load segment. Results come back through the TestRun status, signed callbacks and the metrics store. Pods never write to the database directly.

02 · Architecture

How the parts connect. One Next.js app serves both the dashboard and the API (route handlers); a separate Node worker runs background jobs. Both share packages/core and live in one monorepo with the runner image. Load runs on Kubernetes through the k6 Operator, on a dedicated, autoscaled node pool. The cluster, data stores and Grafana OSS are run by DevOps and managed through GitOps (Argo CD). Images are built by Bitbucket Pipelines. Our dashboard runs tests and shows live and summary charts; Grafana OSS handles deep-dive analysis. Lane headers show the owner.

03 · Safety & abort

Four independent ways a run stops: an engineer's emergency stop (deletes the TestRun), an expired lease, missing health or telemetry data (fail closed), and k6's own threshold abort. Underneath them, Kubernetes enforces two limits the app can't override: NetworkPolicy allows traffic only to approved targets, and ResourceQuota caps total load. The lease path works even if the dashboard and API are both down.
